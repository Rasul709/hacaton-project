# Digital HR: границы MVP и приемка демо

## Назначение и честный статус

Репозиторий уже содержит широкий демонстрационный прототип. Его нельзя считать кадровой системой, источником юридически значимых расчетов или подключенным к 1С:ЗУП/Documentolog. На хакатоне показываем три сквозных сценария: вход под фиксированной демо-ролью, подача/рассмотрение демонстрационной заявки, ответ Jana по локальной базе с указанием записи-источника либо отказ. Остальные разделы — существующие демонстрационные экраны, вне критического пути приемки.

## Объем на защиту

**Обязательно:** вход с фиксированными тестовыми учетками; собственные заявки сотрудника; очередь заявок руководителя назначенного подразделения; просмотр и решение HR; серверная проверка прав на каждом запросе; запись статуса и автора решения; локальный FAQ поиск с проверяемым источником и безопасным отказом; seed-данные; запуск локально; краткая инструкция демонстрации.

**Показываем как макет / исключаем из критериев готовности:** точный расчет отпускного баланса, зарплаты, налогов и кадрового стажа; юридическая применимость календаря и корпоративных норм; настоящие интеграции с 1С:ЗУП, Documentolog, Enbek.kz, eGov, email/SMS; Academy, полноценные уведомления, аналитика, тесты курса, внешняя генеративная модель, Docker/деплой. Не заявлять эти функции как работающие интеграции.

## Явные правила доступа

Роль берется только из аутентифицированной серверной записи пользователя. UI-переключатель/скрытие кнопок не дает прав. Все проверки выполняются сервером после JWT-аутентификации; запрещенный запрос возвращает `403`, отсутствующая/чужая запись для сотрудника — `404` (не раскрываем факт существования чужой заявки).

| Действие/поля | Сотрудник | Руководитель | HR_MANAGER / ADMIN |
|---|---|---|---|
| Свои заявки | Читать, создать, отменить только `PENDING` | То же | Все заявки |
| Чужие заявки | Запрещено | Только сотрудники подразделения, где `department.managerId === user.id`; читать имя, подразделение, тип, даты, число дней, причину, статус, даты решения и комментарий. Адрес, ИИН, зарплата, контакты и вложения не входят в обзор | Все заявки и вложения по служебной необходимости |
| Решение | Запрещено | Только `PENDING` своей команды; approve/reject, причина отказа обязательна | Любая `PENDING`; причина отказа обязательна |
| Сотрудники | Только свой профиль и безопасные поля | Только безопасные поля своего подразделения | Полный кадровый набор; изменения только HR/ADMIN |
| Изменение роли/зарплаты/ИИН | Запрещено | Запрещено | HR/ADMIN по явному endpoint и с аудитом |

Нельзя доверять `employeeId`, `departmentId`, `role` или `reviewerId` из тела запроса: идентификатор автора/решающего берется из сессии, команда — из БД. Руководитель не может передать другой `employeeId`, подменить ID заявки или принять решение повторно. Если команда не назначена, руководитель не видит и не решает чужие заявки.

## Демонстрационные правила заявки

Форма — сценарий прототипа, не юридически значимое заявление. Допустимый вид: календарные дни между датами включительно; демонстрационный счетчик не сверяется с балансом сотрудника и не обещает выплату/приказ. Не показывать начисления, налоги, «остаток» или гарантии соответствия ТК. Запись получает `PENDING`, владелец — только текущий пользователь; смена статуса сохраняет решающего, время и комментарий. Проверки: обязательный тип/причина/даты, дата окончания не раньше начала, отказ без причины невозможен, повторное решение не меняет уже закрытую заявку.

## Jana: поиск, ответ и источники

Для демо используется только локальный детерминированный поиск по ключевым словам в `HR_KNOWLEDGE_BASE`; LLM не является источником кадровых ответов. Запись базы содержит `id`, заголовок, текст ответа, keywords, источник (название документа и раздел) и ответственного редактора/дату проверки. Выбирается запись с наибольшей суммой длин совпавших ключевых фраз; при отсутствии совпадений или score `< 3` возвращается отказ и предложение обратиться в HR. Ответ вместе с источником дословно берется из одной записи; нельзя приписывать ответу модели фиктивный источник или числовую уверенность. Контрольные запросы: «сколько дней ежегодного отпуска» → статья/FAQ про отпуск; «что делать при больничном» → соответствующая запись; «номер моей зарплатной карты» → отказ; «как приготовить плов» → отказ; пустая строка → валидационная ошибка. Владелец базы — назначенный HR-редактор, ревизия перед каждым демо; юридические утверждения без проверенного первоисточника не публиковать.

## Технический контракт и интеграции

Фактический стек: React 19 + TypeScript + Vite; Node.js + Express; Prisma + SQLite в локальной конфигурации (PostgreSQL — только целевая опция, если отдельно настроена). UI → JSON REST `/api/v1` → Express middleware (JWT, роль/область, валидация, аудит) → Prisma/SQLite. Демо работает на локальных seed-данных.

Сценарий заявки: браузер отправляет `POST /api/v1/leave-requests` без автора → сервер берет `req.user.id`, валидирует диапазон → пишет `PENDING` → `201`; список запрашивается `GET /api/v1/leave-requests` с серверным ограничением области → решение `POST /api/v1/leave-requests/:id/approve|reject` повторно проверяет роль, команду и `PENDING`, затем фиксирует результат и audit event. Ошибки: `400` неверные данные/переход, `401` нет/недействителен токен, `403` нет права на действие, `404` нет доступной записи, `409` конфликт статуса, `500` общая ошибка без stack trace клиенту.

1С:ЗУП и Documentolog в текущем проекте не подключены. В презентации описывать только будущий адаптер: входящий импорт сотрудника с внешним ID и идемпотентностью; выходящий пакет согласованной заявки/документа с correlation ID, состояниями `queued/sent/failed`, журналом попыток и ручным повтором. До появления тестового контура, формата обмена и подтверждения владельца системы показывать интеграцию как mock-событие с маркировкой «демо».

## Параллельная работа и резерв (56 часов команды)

Роли назначаются участникам при старте, не выдумываются в документе: A — владелец сценария/приемки; B — API и доступ; C — UI заявки; D — Jana/база знаний; E — сборка, данные и демонстрация (при меньшей команде совмещение A/E и C/D). День 1, часы 0–4: зафиксировать стек, владельцев, seed, контракты и smoke-сценарий. Часы 4–20: B делает авторизацию/область доступа; C форму/список; D FAQ и отказ; A проверяет критерии — параллельно. Часы 20–32: соединение вертикальных сценариев, фиксы. Часы 32–40: приемка и исправления. Часы 40–48: резерв на интеграционные сбои и только затем polish. Часы 48–56: заморозка функций, инструкция, демо-репетиция и запасной сценарий без сети. Интеграционная сборка к часу 20 — блокирующий checkpoint; если не готова, выкидываем необязательные экраны/визуальные улучшения, не сокращая проверку доступа.

## Проверяемые критерии готовности

Демо-связка: `manager@janapost.kz` → руководитель `emp-3`, подразделение `dept-2`; `employee@janapost.kz` → сотрудник `emp-6`, подразделение `dept-2`; внешний сотрудник для запрета → `emp-5`, подразделение `dept-5`. Тестовые пароли только локальные demo; не переиспользовать в проде.

1. Сотрудник создает заявку: `201`, владелец `emp-6`, статус `PENDING`; видит ее в списке.
2. Сотрудник запрашивает список с `employeeId=emp-5`: сервер все равно возвращает только свои записи (или отклоняет запрос `403`).
3. Сотрудник запрашивает `/leave-requests?employeeId=<чужой-id>` либо отменяет чужую заявку по ID: ответ не содержит чужих данных и состояние не меняется (`403` для отмены).
4. Руководитель `dept-2` видит заявку `emp-6`, но не видит/не решает заявку `emp-5` из `dept-5`; изменение URL/ID не расширяет команду.
5. Сотрудник напрямую вызывает approve/reject: `403`; HR может принять `PENDING`, и запись содержит actor, timestamp, результат.
6. Повторное approve или reject завершенной заявки: `409`; состояние и audit trail не дублируются.
7. Jana: 2 контрольных HR-вопроса получают ответ из ожидаемой записи и ее точный источник; минимум 2 не относящихся к базе запроса получают отказ без источника.
8. Демонстрационная заявка не выводит сумму зарплаты/налогов/остатка и явно помечена как mock.
9. Чистый checkout запускается по README, seed восстанавливает эти IDs, основной happy path проходит без внешней сети.

## Исправления перед заявлением о готовности

Исправлено в прототипе: API ограничивает видимость и решения руководителя его командой из БД; повторное решение и отмена закрытой заявки отклоняются; mock login принимает только фиксированные демо-email с паролем `password123`; форма больше не показывает фиктивную сумму отпускных; сгенерированному LLM-ответу не приписывается фиктивный источник. Тестовый сценарий по-прежнему требует выровнять демо-связку сотрудник/подразделение/руководитель и пройти критерии приемки; до этого документ описывает целевое поведение, а не подтвержденный результат тестирования.
